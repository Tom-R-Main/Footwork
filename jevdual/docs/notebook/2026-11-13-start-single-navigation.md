# A browser start that launches Chrome loads its page twice

Found while the filmed page pointer's probe first ran against a real window (FP74 in
2026-11-12-filmed-page-pointer.md): the fixture logged two documents for one start. This file
establishes the cause from the code and the retained runs, and registers the change. No window was
opened for it.

## SN1 · update · 2026-11-13 12:35
Observed: start --browser --url U gives the URL to the browser twice. First as an argument of the launch: session._start_browser passes U to the holder's spawn (or, without a holder, to bind_footwork_chrome), which passes it to browser_driver._begin_chrome, whose launch command ends with U, so Chrome opens its first tab on U. Second as a navigation: once the tab is bound, _start_browser calls bridge.navigate(U), which is the driver's Page.navigate on that same tab. Both are in the first browser-mode commit (bdfe2c7, 2026-09-25) and neither has changed since. The first happens only when this start launches the browser, or when it finds one running with no window and opens one (the recovery helper is given U too). A start that finds Footwork's Chrome running with a window launches nothing and loads U once, by the navigation. In the two complete live runs of the filmed page pointer's probe, each a start that launched its own Chrome, the fixture's log holds two documents: the first posted "loaded" and one beat and was replaced 0.75 s and 0.80 s later by the second, in which every step ran (results/filmed-page-pointer-20261112/fp67-run2 and fp88-slot1, page-events.jsonl). The driver's navigate answers when the navigation is committed, not when the page has loaded; start then waits two seconds and observes.
Inferred: the navigation is the intended one and the launch argument is the duplicate. The navigation is the only one of the two that happens on every path, that returns an effect start can refuse on ("a session must not start bound to whatever page the browser already showed"), and that goes through the driver's own checks. The launch argument does nothing the navigation does not, except on the path where a caller binds and never navigates, which start is not. What the duplicate costs: the page's load-time effects happen twice (a single-use link in the URL is spent by the first load and refused on the second; a counter or a GET with an effect runs twice); the first document runs for most of a second and is then discarded with whatever it had begun; a server sees two requests for one start; and any harness that reads the page's own log must tell the documents apart, as the probe had to. This is different from a reload the operator asks for (the navigate command, or a page reloading itself), which is one deliberate load each time and is not touched.

## SN2 · prediction · 2026-11-13 12:35
Question: does launching the browser on a blank page, when start is going to navigate anyway, leave exactly one load of the start URL on every path, without changing a start that gives no URL or a caller that binds without navigating?
Hypothesis: yes. When start has a URL it gives the launch about:blank in its place (to the holder's spawn or to the direct bind) and navigates once as now. about:blank and not no argument, because a Chrome launched with no URL opens its new-tab page, which is a page of its own with network requests of its own, and because the recovery helper already uses about:blank when it has no URL. A start with no URL passes none, as now. bind_footwork_chrome, the holder and the launch keep their signatures and their meaning (the URL they are given is what the launch opens), so the scripts that bind with a URL and never navigate are unchanged.
Alternatives: (a) keep the launch URL and skip the navigation when this start launched the browser and the tab already shows the URL (then the fresh path has no navigation effect to refuse on, a redirect makes the comparison wrong, and the two paths differ); (b) the first load is wanted, to warm the page before the observed one (nothing in the code or its history says so, and a second request is not a warm page for anything with load-time effects); (c) something between the bind and the navigation needs the real page in the tab: the filmed setup reads the window's web area there, and a blank page may show none or a different frame (not decidable without a window; it is the live check).
Test: composed, launching nothing: for a start with a URL, on the holder path and on the direct path, the launch is given about:blank and the navigation the URL, so the URL reaches the browser once; with no URL the launch is given none and nothing is navigated; the holder's command line carries about:blank through to its own launch; bind_footwork_chrome called with a URL still launches on that URL. At the level of Chrome itself, with no window: a headless Chrome on a scratch profile and port, launched on a local page's URL and then navigated to it, fetches it twice; launched on about:blank and then navigated, once. Live, when a window is next available for other work: one unfilmed start with a URL on a fresh profile, and the filmed probe, whose log should then hold one document.
Predicts: the composed tests fail on main and pass with the change, and no existing test changes its outcome; headless, two requests before and one after. Live (not run here): one document in the probe's log, the start's first observation showing the page loaded, and a filmed start still finding its web area.
Against: an existing test that depended on the launch URL; headless, a count other than two and one; live, a filmed start refused for want of a web area on the blank page, or a first observation taken before the page has loaded where it was not before.
