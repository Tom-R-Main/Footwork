# A browser start that launches Chrome loads its page twice

Found while the filmed page pointer's probe first ran against a real window (FP74 in
2026-11-12-filmed-page-pointer.md): the fixture logged two documents for one start. This file
establishes the cause from the code and the retained runs, and registers the change. No window was
opened for it.

## SN1 · update · 2026-11-13 12:35
Observed: start --browser --url U gives the URL to the browser twice. First as an argument of the launch: session._start_browser passes U to the holder's spawn (or, without a holder, to bind_footwork_chrome), which passes it to browser_driver._begin_chrome, whose launch command ends with U, so Chrome opens its first tab on U. Second as a navigation: once the tab is bound, _start_browser calls bridge.navigate(U), which is the driver's Page.navigate on that same tab. Both are in the first browser-mode commit (bdfe2c7, 2026-09-25) and neither has changed since. The first happens only when this start launches the browser, or when it finds one running with no window and opens one (the recovery helper is given U too). A start that finds Footwork's Chrome running with a window launches nothing and loads U once, by the navigation. In the two complete live runs of the filmed page pointer's probe, each a start that launched its own Chrome, the fixture's log holds two documents: the first posted "loaded" and one beat and was replaced 0.75 s and 0.80 s later by the second, in which every step ran (results/filmed-page-pointer-20261112/fp67-run2 and fp88-slot1, page-events.jsonl). The driver's navigate answers when the navigation is committed, not when the page has loaded; start then waits two seconds and observes.
Inferred: the navigation is the intended one and the launch argument is the duplicate. The navigation is the only one of the two that happens on every path, that returns an effect start can refuse on ("a session must not start bound to whatever page the browser already showed"), and that goes through the driver's own checks. The launch argument does nothing the navigation does not, except on the path where a caller binds and never navigates, which start is not. What the duplicate costs: the page's load-time effects happen twice (a single-use link in the URL is spent by the first load and refused on the second; a counter or a GET with an effect runs twice); the first document runs for most of a second and is then discarded with whatever it had begun; a server sees two requests for one start; and any harness that reads the page's own log must tell the documents apart, as the probe had to. This is different from a reload the operator asks for (the navigate command, or a page reloading itself), which is one deliberate load each time and is not touched.
