# Filmed pointer to page targets (B7, second step)

Step B7 of `docs/repo-learning/app-adaptation/REPORT.md`, continued from ea8933b: a `start --browser`
session can film the real pointer (park, point), but its page actions do not move the pointer to their
targets, because the driver's page observation carries no element geometry. DemoGeek's take script
today reads rectangles through its own DevTools client and moves the pointer with its own glide.py;
the goal is one reusable page and pointer layer in Footwork. Branch claude/b7-filmed-browser-20261112
from main c7cac4f. Nothing is upstreamed.

## FP1 · prediction · 2026-11-12 11:29
Question: can a filmed browser session move the real pointer onto the page element it is about to click or type into, using geometry the driver already computes?
Hypothesis: the driver's semantic snapshot reads every node's layout bounds from DOMSnapshot.captureSnapshot in document coordinates and the visual viewport's scroll offset and size from Page.getLayoutMetrics (cua-driver-core browser/semantic.rs parse_layout, parse_viewport), using them only to classify visibility; it drops both before serializing a ref (tools.rs semantic_ref_value). A main-frame ref that is in the viewport has a viewport rectangle equal to its bounds minus the scroll offset, clipped to the viewport, in CSS pixels. Emitting that rectangle (null for child frames and for refs not in the viewport) and, in a filmed session, approaching its centre through Filmed.viewport (content origin plus CSS px at 100% zoom) before the page click or type puts the real pointer over that element.
Alternatives: (a) DOMSnapshot bounds are not in the same coordinate space as cssVisualViewport's pageX/pageY (for example on a zoomed page or a page with a pinch-zoom offset), so the rectangle is offset; (b) Filmed's content origin is off by the toolbar or a scale factor, so the pointer lands beside the target; (c) the approach's real mouse-moved events change the page (hover menus) so that the following synthetic click hits a different state; (d) a layout change between the observation and the approach moves the target.
Test: a Rust unit test of the rectangle on composed nodes (offset, clipped, null in a child frame and out of the viewport); Footwork unit tests of the filmed browser act (approach to the mapped centre before the driver call, refusal with nothing sent when a target has no rectangle or the take has ended, no change when not filmed); then a live run on an isolated profile and port 9466 in a granted window: a filmed browser session on a fixture whose buttons log every trusted pointer event's target, clicking three buttons at different positions, one after scrolling.
Predicts: Rust and Footwork tests fail before the change and pass after; every existing browser and session test passes. Live: before each click handler runs, the page logs a trusted mouseover or mousemove whose target is that button, and the recorded gesture ends inside the button's screen rectangle; the scrolled case does too.
Against: a trusted pointer event's target is not the button about to be clicked, or the gesture ends outside it; any existing test failing.

## FP3 · update · 2026-11-12 17:54
Observed: Sol's review of 7da1212 (5/10, three P1) and two readings of source that confirm its first two findings. (1) Chromium's DOMSnapshot agent reports layout bounds from AbsoluteBoundingBoxRectF with no zoom adjustment, in physical pixels (inspector_dom_snapshot_agent.cc RectInDocument), while Page.getLayoutMetrics divides cssVisualViewport's page offset and client size by LayoutZoomFactor, the page zoom times the device scale factor (inspector_page_agent.cc, "visible_contents is in physical pixels"). The rects1 patch subtracts and clips one against the other, so on a display with scale factor 2, or at any page zoom but 100%, its rectangle is wrong; on this Mac that is every run. (2) The driver's page click calls DOM.scrollIntoViewIfNeeded on the ref's node after the bridge's approach has finished (cua-driver-core browser/tools.rs, the dom_event branch), so a partly visible target moves away from the parked pointer before the click. Sol also found that the rectangle's centre is not hit-tested (a partial overlay or an overflow clip leaves another element there), that a refused approach is reported as nothing sent after pointer events were posted, that the live probe could signal a Chrome it did not start and pairs its evidence by label only, and that PROVENANCE.md names the previous version.
Inferred: FP1's alternative (a) holds on source evidence: the snapshot's bounds and the viewport metrics are not in one coordinate space. The geometry has to come from where the click's own comes from, the live node in CSS viewport pixels, read after the click's scroll and hit-tested, and it has to be read again after the approach. The same unit mismatch means the unpatched driver's in_viewport and offscreen classification is unreliable at scale factor 2; that is upstream behaviour, not measured here, and outside this package.
Changes: none yet. The rects1 step is withdrawn before any live run and was never released.
Resolves: FP1 = inconclusive

## FP4 · prediction · 2026-11-12 17:54
Question: can a filmed browser session put the real pointer on the element a page action is about to act on, using the live position the driver's click itself computes?
Hypothesis: the driver's page-route click already resolves the ref's node, refuses a detached one, scrolls it into view and dispatches its events at the centre of the node's getBoundingClientRect, on the element document.elementFromPoint returns there. Those are CSS pixels relative to the viewport, the space Filmed.viewport maps to screen points when the page zoom is 100% and the pinch scale is 1. A locate_only option on browser_click that runs the same checks and scroll, then returns that rectangle, whether the element at its centre is the node or inside it, the border-box centre from DOM.getBoxModel as a check that does not run page script, and the viewport's zoom and scale from Page.getLayoutMetrics, and dispatches nothing, gives the bridge what it needs: locate, refuse unless the centre hits the target at zoom 1 and scale 1, approach, locate again and refuse if the centre moved more than 2 px or no longer hits the target, then act.
Alternatives: (a) getBoundingClientRect and elementFromPoint disagree with where the real pointer lands (a visual viewport offset, a transformed ancestor, a browser toolbar that changes Filmed's content origin after start); (b) the approach's real hover changes the page so the second locate refuses targets a person could click (a tooltip over the centre, a hover-expanding row); (c) the click's own scrollIntoViewIfNeeded scrolls again after the second locate; (d) the page replaces the built-ins the locate script uses.
Test: Rust mock-CDP tests of locate_only (the reply's fields; nothing dispatched and no cursor drawn; refused for a detached node as the click is; a child-frame ref reported unavailable; a centre that disagrees with DOM.getBoxModel's reported). Footwork unit tests of the filmed act: the order locate, approach, locate, act; refusals with no page action for no hit, a zoomed or scaled viewport, a child frame, and a target that moved during the approach, the last saying the pointer moved; an unfilmed session makes no locate call. Then the live probe on port 9466 in a granted window, on a display with scale factor 2: three buttons, one below the fold, one partly out of view, and one whose centre a fixed overlay covers.
Predicts: the Rust and Footwork tests fail before the change and pass after, and every existing test passes. Live: for the three buttons the page's last trusted pointer event before each click handler targets that button and the gesture ends inside the button's rectangle as the page reports it at click time; the covered button is refused with no click handler run and no gesture toward it.
Against: a click handler runs whose last trusted pointer event was on another element; a gesture ending outside its button; the covered button clicked; an existing test failing.

## FP5 · update · 2026-11-12 18:18
Observed: FP4's design changed twice while it was being built, before any of its tests could count. (1) browser_click is an action tool: the driver replaces a successful action's structured content with its closed ActionResult (cua-driver-core tool.rs publish_action_result) and has no effect word for a call that dispatches nothing, so a locate block returned from the click would not reach Footwork. The locate is therefore a third, read-only mode of get_browser_state (locate_ref), not an option on the click. (2) A read tool should not scroll, so the locate scrolls nothing; Footwork instead refuses, in a filmed take, a target that is not wholly inside the viewport, because the click's own scrollIntoViewIfNeeded would move it after the pointer arrived. Scrolling a filmed page is a separate primitive (REPORT.md step D). With that design: on the connected4 tools with the new mock-CDP tests, all five fail; with the change every cua-driver-core library test passes (1250, no warnings). On main's python with the new tests, 29 of 48 filmed tests fail; with the change all pass. These runs happened before this entry was written, so they are results, not predictions.
Inferred: the driver and bridge do what the revised design says on composed inputs. Whether getBoundingClientRect, DOM.getBoxModel and Filmed's content origin agree with where the real pointer lands on this display is still only testable live.
Changes: driver chain step ref-locate (version connected4.locate1) replaces the withdrawn snapshot-rects; CuaBrowserOperations.locate and the held route's locate; BrowserBridge locates, approaches, locates again and only then acts, refusing target_unlocated before the pointer moves and target_moved after, the latter saying the pointer moved; an ended take refuses a navigation; a contended approach's refusal says how many pointer events were posted; the live probe closes only a Chrome its own start launched, needs a fresh profile and output directory, and matches each step's evidence by time and gesture order.
