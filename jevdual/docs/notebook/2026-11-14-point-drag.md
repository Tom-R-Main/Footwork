# A real-pointer drag between two points

For the second cross-app film (Excalidraw: boxes and arrows drawn on a canvas). The film's own
player drives the page through DevTools and moves the pointer itself; it has no drag. This file
establishes what Footwork already has, what is missing, and registers the one command that fills it.

## PTD1 · update · 2026-11-14 00:13
Observed: read on main at 85c504f and in the installed release 6d571a1. jevdual.drag plans and plays a real-pointer drag in global screen points: press, a 120 ms hold, drag events along a planned path with no gap over 50 ms, a 150 ms settle, release; every exit after the press releases exactly once; an abort posts Escape first; under 6 points is refused before anything is posted; foreign key and button presses and a pointer that is not where the last post put it stop it. Its one caller is the native session route, footwork do drag SOURCE DESTINATION, which takes two elements of the observation and drags centre to centre; browser mode refuses drag before dispatch. That route was run live in Chrome on 2026-11-05 (2026-11-05-pointer-drag.md, PDU3): the page's handlers logged 92 and 71 pointermoves and both drops landed. Nothing takes two points. Three facts about the caller this is for, read from its files and Footwork's: its page actions go through its own DevTools connection, and a Footwork browser session refuses to send while another DevTools client is connected to the browser (browser_session_holder.second_client_refusal); it moves the pointer between actions with its own helper, and a filmed Footwork take ends when the pointer is moved between its commands; a canvas has no element at either end of a box or an arrow.
Inferred: what is missing is an entry point, not an engine: two points in, the existing approach and drag out. It cannot be a browser session (second client) and cannot be a filmed session's command (the caller moves the pointer in between), so it is a command that belongs to no session and makes no DevTools connection. It still has to respect the desktop's ownership, which a session gets from the command entrypoint's claim.

## PTD2 · prediction · 2026-11-14 00:13
Question: can one command, with no session, drag the real pointer from one screen point to another through the existing engine, refusing whenever it cannot own the desktop, and always leaving the button up?
Hypothesis: yes. footwork drag-points X0 Y0 X1 Y1 --mode exclusive_desktop takes global screen points (top-left origin, the space of the engine and of the caller's own pointer helper). It claims the desktop in the coordination registry for its duration, under an owner the caller names, and is refused when another owner holds it. It refuses, posting nothing, without --mode exclusive_desktop, when either point is on no display, when the left button is already down, and when the drag is under 6 points (the engine's rule). Otherwise it moves the pointer to the start with the button up (the engine's play_move), plays the drag (play_drag), reads the button afterwards, and prints one JSON object saying what happened and where it released. With --record FILE it appends the same pointer_gesture/1 record a filmed drag writes, with the window and content origins null because it has no window. Exit 0 only for a drag released at its end point.
Alternatives: (a) points for the session route, footwork do drag --from X,Y --to X,Y in a filmed session (ends the take as soon as the caller's own helper moves the pointer, and a browser session cannot share the caller's Chrome); (b) viewport CSS px with a content origin as arguments (the caller already maps to screen points for its pointer helper, and an origin passed in is one more thing to get wrong); (c) no claim at all, as the caller's own pointer helper does (a second owner could then be mid-gesture on the same desktop).
Test: composed, with the poster and clock stood in for and a registry in a temporary directory: a drag between two points posts approach moves with no button, one press at the start, drag events, one release at the end, and exits 0 with the JSON saying so; each refusal posts nothing and names its code; with the desktop reserved by another owner the command is refused and posts nothing; foreign input during the drag gives Escape, then one release where the pointer was, a nonzero exit and the release point in the JSON; an approach that stalls never presses; --record appends one line whose posted events are down, drags and up. Live, one screen slot, on a page that is one canvas logging its pointer events, in a Chrome launched for it and no DevTools connection: one drag; one drag interrupted by an injected key press; one drag too short.
Predicts: composed, the tests fail before the command exists and pass with it, and no existing test changes. Live: the page logs exactly one pointerdown and one pointerup, both trusted, each within 1 CSS px of its point, every pointermove between them with the button held and on the canvas, no gap over 50 ms after the first move, and the button reads up afterwards; the interrupted drag logs one pointerdown and one release and the command says where it released; the short one logs nothing.
Against: an existing test changing its outcome; any path that leaves the button down or releases twice; a press posted on a path that should refuse; live, a press or release more than 1 CSS px from its point, a move with the button up between them, or a pointer event on anything but the canvas.
