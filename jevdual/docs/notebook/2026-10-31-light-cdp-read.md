# Light profile L3a-1: direct-CDP browser, owned launch and read-only observation

## LCD1 · prediction · 2026-10-31 11:40
Question: can Footwork own a headless Chrome and observe a page through its own CDP client, with no CUA and no browser-use, in the shape the bridge already consumes?
Hypothesis: a Chrome launched by Footwork with `--remote-debugging-port=0` into a fresh profile directory is reached only through the browser endpoint its own DevToolsActivePort names, after the endpoint's reported browser process matches the launched pid and start time. A snapshot composed from Accessibility.getFullAXTree, DOM.getDocument (pierce) and DOMSnapshot layout, following CUA's role, action and state rules at d5373879 (semantic.rs), gives BrowserBridge a WebMenu whose candidates match the fixture page's declared controls. Every ref binds browser incarnation, browser context, target, frame, loaderId and backend node.
Alternatives: headless Chrome omits or reshapes AX properties CUA relies on (states, values, editable); the DevToolsActivePort file can be stale or written by another process; DOMSnapshot layout and AX backend ids do not join for some controls.
Test: real headless Chrome 156 against a loopback fixture with a button, a text field holding a value, an empty field, a password field holding a value, a checked checkbox, a disabled button, an offscreen link and a same-origin iframe. Assert candidates (label, role, operations, value, checked) against the fixture declaration. Controls: a stale DevToolsActivePort is refused; an endpoint whose browser pid differs is refused; the password value never appears; iframe content is reported omitted, not silently absent; click and type refuse with dispatched=False and the transport log shows no Input, Runtime.callFunctionOn, DOM.focus or Page.navigate call; a reload between observe and act changes the loaderId and invalidates refs. Unit tests cover the transport (id correlation, error replies, disconnect leaves in-flight calls unknown, timeout) without Chrome.
Predicts: candidates equal the declared controls; disabled controls carry no operation; the offscreen link is marked offscreen; every negative control refuses before any mutating CDP method; nothing outside effectors/cdp imports websockets.
Against: any declared control is missing or mislabeled, a password value is exposed, a stale or foreign endpoint is accepted, a mutating method is sent, or a reload leaves old refs usable.

## LCDU1 · update · 2026-10-31 11:50
Resolves: LCD1 = failed
Observed: the first real headless Chrome 156 run gave five extra candidates beyond the fixture's declared controls: each input's inner editor (generic, editable) and inner text from its user-agent shadow tree, including the password field's text as a label of one bullet per character. The composer kept AX nodes whose DOM node lies outside the observed DOM, as CUA's compose_accessibility_tree does. Everything else predicted held on that run: identity checks, disabled and offscreen controls, the iframe reported as omitted, refusals before dispatch, the reload invalidating refs, no mutating method sent.
Inferred: a control's user-agent internals are part of the host control. Skipping AX nodes whose backend id is outside the main-frame DOM index removes them without losing a declared control. The password-only assertion on page text would have missed the leak; the test now checks labels, values and the value map.
Changes: snapshot.py skips nodes outside the DOM index; tests assert neither the password nor its length appears anywhere in the observation.
Next: with the fix, the same unchanged predictions pass (13 tests, three on real Chrome; full suite 2535 passed). This rerun was not preceded by a separately committed prediction; it tests LCD1's original Predicts against revised code. Then L3a-2: mutations within one connection (DOM-event and trusted click, insertText with exact pre/post value readback), with its own prediction, before any CLI selection.
