# Q7. Should the arbiter learn?

Status: pre-registered 2026-09-21. Last, because it needs repeated visits and a memory mechanism.

## Observation

Dual-process systems shift toward fast responses as experience accumulates [A4][A12][A14];
structured per-site memory that separates task logic from action details transfers across sites
[H2]. jevdual has no memory: every visit to a site starts cold.

## Hypothesis

A per-site memory of (page type, action, outcome) lowers escalations per task on repeat visits.

## Predictions

If true: escalations per task fall across five rounds with memory on (negative slope, interval
excluding 0) and stay flat with memory off; pass rate does not fall.

If false: the slopes do not differ, or memory on raises false completions or repeats a wrong action.

## Design

Five rounds of `live-dev` on the same sites, memory on versus off, same task order. Memory: per
origin, S1 records (page signature, chosen operation, effect observed) and the arbiter reads the
matching record as one extra noul input ("this action worked here before"). Primary metric:
slope of escalations per task over rounds. Guardrails: pass rate; false completions; repeated
wrong actions (the memory must not entrench a mistake).

## Decision rule

Supported: memory joins the default. Falsified: no memory; the extra noul is removed. Guardrail
breach: memory records are made outcome-gated (only actions whose effect matched the operation are
stored) and the experiment reruns once.
