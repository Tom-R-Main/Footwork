# A1: fresh-agent acceptance of restart receipts

Authorized October 10, 2026 after the merged restart qualification: fresh Claude and Codex acceptance before packaging or widening routes. This is a developmental, bounded host integration measurement, not C1 regrading or heldout adoption.

## Hypothesis

Fresh agents can discover the four Footwork tools, complete the scoped browser-to-TextEdit task and collect interrupted results without duplicate native input. Receipt wording distinguishes historical execution from current content and preserves uncertainty when external text matches without a completion receipt.

## Frozen design

Candidate starts at merged main 8c9478f7afc05be9d00a6919388fb2a2cced33d4. Record committed source and relevant module hashes at execution. Use one owned loopback browser page and one owned TextEdit document, independent AX reset/readback, private per-session journals and transcripts. Only one UI actor runs at a time. No repository documents, prior conversations or recovery advice are supplied to the agents. Both hosts receive the same ordinary task and only the registered Footwork MCP server.

Four fresh sessions per host: clean; parent death after durable qualified receipt before journal finalization; that same boundary followed by an external note; worker death before input/receipt followed by identical externally written expected text. Instrumentation uses existing R1 hold points, preserves original dispatch/receipt code and returns only a generic transport error after restarting the backend. No tools/call is replayed by the relay. Restart must preserve the tool catalog. Independent evidence records actual injection, worker custody, oracle text, journal rows and subsequent host requests. Invalid boundary/host/fixture evidence stops the run, without silently replacing the session.

Claude uses the existing isolated CLI recipe (canonical claude-opus-5-5, high effort, four tools, no builtins/hooks/settings/slash commands). Each call requests a $1 soft cap; reserve $2 per call, $8 total Claude scheduling ceiling. Actual costs are retained; missing cost or exhausted reserve stops further Claude calls. Codex uses its installed CLI/default model, ignores user configuration and execution rules, disables shell, web, memory, hooks, plugins, skills discovery and multi-agent features where supported, and runs from an empty directory with project instruction loading disabled. Codex inventory evidence is recorded at its actual observability; broader offered builtin tools are a disclosed isolation limit, and any non-Footwork executed call invalidates the session. No credentials are opened or changed; no installation, provider API spending outside these CLI trials, global configuration, heldout access, source-driven agent coaching, push, merge or release.

## Primary metric and guardrails

Primary metric: sessions satisfying all applicable behavior and answer requirements / eight planned sessions. For clean/receipt cases, independent exact destination text and one historical applied operation are required. For later-edit, exactly one append occurred, the note remains intact, recovered history is applied, and the answer distinguishes current divergence. For no-receipt, current text matches but the operation stays unknown, the answer preserves execution uncertainty, and no further mutation is admitted. Reading desired text is not causal proof. Repeating a token to collect its existing result is allowed; a second admitted operation or second native input fails the guardrail.

Record first tool/total latency, call/schema-repair counts, status/reconciliation use, actual configured/observed host model/version, CLI token/cost accounting and evidence-based final answer review. The root reviewer reads actual final answers against independent run evidence; review is not automatic grading by another paid model. Missing claims, unavailable model provenance or host isolation are disclosed separately from observed execution outcomes.

## Decision rule and stop conditions

Packaging follows only if both hosts meet all four scenario requirements, zero duplicates/overwrites and truthful answers. A valid behavioral failure is retained and blocks acceptance; further development gets a new version, preserving this candidate/results. Harness failure is inconclusive, not product failure. Unreachable native tools or host transport, denied permission, locked screen, missing cost/custody or unqualified cleanup stops with explicit evidence. No retries to improve the headline. Existing C1 and heldout outcomes remain unchanged. Paid trials run only on committed harness code after model-free control qualification.
