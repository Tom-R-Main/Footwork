# Q12b. With input that arrives, do receipts cost the driver less than "Clicked"?

Pre-registered 2026-09-26, before any measured run. Build: the commit that adds this file (package C's
input fix, 7eddfff; package D's receipts, 39d24c6 and e2d1549). Background: Q12
(`docs/experiments/Q12.md`, `results/q12-live-dev.md`), package C (`docs/notebook/2026-09-26-c-trusted-input.md`),
package D (`docs/notebook/2026-09-26-d-receipts.md`).

## Observation

Q12 found H0(b): receipts shortened the way to the same failure. On saucedemo no route existed, because
Chrome's breached-password warning dropped every click after the login (package C); a receipt can only
help where another route exists. Package C removed the warning from the agent's browser. Package D
made receipts say whether the page received the input, and report scrolling, a focus move and a
navigation between steps, which Q12's docs-page receipts could not ("literally true and useless").

## Hypothesis

H1: on the repaired input path, delivering receipts (to the driver's action result and the verifier's
trajectory line) lowers requests per unit of progress against recording them only.

H0 alternatives: (a) no difference: with input fixed the no-op clicks that receipts address mostly
vanish, and what remains (docs pages, sort controls) does not change the driver's plan; (b) raw
requests fall with progress unchanged, as in Q12; (c) receipts hurt: no-fact refusals up or verified
passes down by more than 2 pooled.

## Arms (enforcement identical, both on the fixed profile)

| arm | receipts | the driver sees | the verifier sees |
|---|---|---|---|
| `guarded` | recorded in the trace only | browser-use's own result text | Q11's trajectory lines |
| `guarded_receipts` | recorded and delivered | the result text plus the receipt, with delivery and "also ..." facts | the same line with the effect word, an `effect` field and `input` when the input never arrived |

## Predictions

Pooled over three runs, paired by task against `guarded`:

- If H1: requests per unit of progress Δ(receipts − guarded) with its bootstrap interval below 0;
  verified passes no worse than −2 pooled.
- H0(a): the interval includes 0 and raw requests move less than ±5%.
- H0(b): raw requests down with their interval below 0, the primary's interval including 0.
- H0(c): verified passes down by more than 2 pooled with no-fact refusals up.

My expectation, written before the run: H0(a). The input fix removes most of Q12's no-op clicks on
both arms, so the receipts have less to say.

## Design

- Tasks: live-dev, 59 tasks, `--live`. Three runs, task-major with both arms interleaved:
  `uv run python -m evals.runner --split live-dev --live --arm guarded --arm guarded_receipts --llm meta --out results/q12b-live-dev-r{1,2,3}`.
- System 2: Muse Spark 1.3 over the Meta Model API; Jev and verifier unchanged; `--max-steps 25`.
- Pooling and tools as Q12: `jq -s add` into `results/q12b-live-dev-pooled/`;
  `evals.paired ... --arm guarded_receipts --vs guarded`; `evals.burden ... --vs guarded`;
  `evals.rejections --arm` per arm.
- Cost: about $1.10 per run.
- Smoke before run 1: `ls-add-backpack-cart` and `lw-pydocs-keyerror` on both arms, once; it also
  settles the saucedemo part of notebook D1 (no `not_delivered` receipt on the fixed profile).

## Primary metric and guardrails

Primary: requests per unit of progress, paired Δ(receipts − guarded) with its bootstrap interval, over
the tasks with some progress (checkpoints reached plus a passed predicate) in both arms; the population
size is reported beside it. Reported next to it, never in its place: raw requests per task, all-task
verified passes, the terminal-mode table.

Guardrails against `guarded`: verified passes no worse than −2 pooled; no false completion the silent
arm lacks; every unauthorized consent run stopped before the committing action; no-fact refusals not
up by more than the silent arm's own run-to-run spread; `undelivered_inputs` zero on both arms (a
nonzero count is an input fault to diagnose first, not a receipt result).

False-receipt audit: every `suspected_noop` receipt whose next step landed on a different URL, and
every `not_delivered` receipt, listed with its step.

The input fix's gain is not credited to receipts: both arms have it. Q12's `guarded` and Q12b's
`guarded` are compared descriptively only (verified passes, saucedemo pauses), to report what the fix
did; they are different days and not paired.

## Decision rule

- H1 supported: receipts become the default on every arm with a System 2 (the silent arm is retired);
  the README gets the number; v6's L2 gains a burden claim and L3 is confirmed.
- H0(a) or H0(b): receipts are kept and delivered as an honesty measure (they are true, and the
  delivery field is how a lost input gets caught), not claimed as a burden reduction.
- H0(c): not adopted; the traces say which done texts quoted receipts, fixed before any rerun.

## Amendment before run 1 (2026-09-26)

The smoke (`results/q12b-smoke-20260926`) showed receipts on steps that dispatch nothing (`wait`,
`extract`, `search_page`) reading "suspected no-op". Such steps now get no receipt
(`jevdual.delivery.READ_ONLY_ACTIONS`). The change is on both arms (the silent arm records the same
receipts), so it moves `noop_receipts` on both and cannot favour either; Q12's no-op counts are not
comparable with Q12b's. The smoke confirmed zero undelivered inputs and a passing saucedemo add on both
arms.

## Result (2026-09-26)

`results/q12b-live-dev.md`. The primary moved (requests per unit of progress −0.28 [−0.69, −0.01]) but
verified passes fell 4 pooled and no-fact refusals rose (67 against 50): H0(c) by the rule as written.
Receipts are not adopted on the driver's side; the delivery guardrail found a false `not_delivered` on
`select_dropdown` (fixed). The input fix, not receipts, is what moved verified passes (121 to 137 on
`guarded` against Q12, descriptive).
