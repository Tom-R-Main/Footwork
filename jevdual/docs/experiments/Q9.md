# Q9. Does System 2 directing System 1 beat System 1 taking the next step from the front?

Status: pre-registered 2026-09-21 22:10. Supersedes the separate designs of Q4 (delegation) and Q5
(extraction as selection) as one four-arm experiment; those files stay as the record of the
individual hypotheses. Depends on: the guarded arm, the call-economy changes, ledger semantics, one
bounded delegation workflow, one evidence-selection workflow.

## Observation

Two live runs on the same 55 tasks (`results/q6-live-paired.md`): the reactive dual agent takes
about 40% of steps on Jev at a median 1.4 s per step against 15.7 s for a Muse step, uses 26% fewer
LLM calls than stock, has zero false completions, and still costs 1.32× stock and finishes no
faster, because every step first consults S1 (458 Jev calls for 196 LLM calls) and the misses are
S1 flailing until System 2 takes over and reaches for `evaluate`. The loop being measured asks Jev
to infer the current subgoal, resolve dependencies, pick an operation and ground it, from the whole
task, every step. `act_toward_goal` exists but is not wired into the evaluated agent; `subgoal` is
never supplied; the grouped-target confidence is a product of two confidences, not a success
probability.

## Hypothesis

Given the same guard (gate and done verification), System 2 that plans and delegates bounded
subgoals to S1 completes more subgoals per System 2 intervention and more tasks per dollar than the
reactive dual agent, and adding S1 evidence selection on read tasks lowers System 2 tokens without
losing needed evidence.

## Arms (verification identical across arms)

| arm | what it tests |
|---|---|
| `guarded` | System 2 alone with the gate and done verification; the fair baseline |
| `dual` | the current reactive agent, after the call-economy changes |
| `delegate` | System 2 with `act_toward_goal` bounded delegation (subgoal, allowed operations, known values, stop condition, budget; `reached` needs observed support) |
| `delegate+evidence` | delegation plus `find_evidence` on read tasks (Jev selects spans and judges answer presence; System 2 synthesises from the packet) |

`stock` and `s1_only` run as reference rows, not as comparators.

## Predictions

If true: on the same tasks, `delegate` has (a) verified completions ≥ `dual` (paired interval not
excluding 0 on the downside by more than 2 tasks), (b) cost per verified completion ≤ 0.8 × `dual`,
(c) completed subgoals per System 2 intervention ≥ 1.5 (dual's equivalent, S1 steps executed per
escalation-free stretch, is the reference), and `delegate+evidence` has System 2 tokens on read
tasks ≤ 0.7 × `delegate` with verified completions within 2 tasks and zero missing-evidence failures
(a read task failed because the packet omitted the needed span, judged from the trace).

If false: `delegate` costs more per verified completion than `dual`, or completes fewer tasks by
more than 2 with the interval excluding 0, or subgoals per intervention stays below 1.2; or the
evidence arm loses more than 2 tasks to missing evidence.

Discriminating prediction against the guard alone: if `guarded` matches `dual` and `delegate` on
completions and cost, S1 adds nothing but speed on the steps it takes, and the product claim reduces
to the guard.

## Design

Tasks: `live-dev` (55) plus the fixture dev split for the destructive and consent cases. One run per
arm, paired by task, bootstrap intervals (`evals.paired`). Primary metric: cost per verified
completion. Secondary: verified completions, System 2 calls and tokens, median and p90 task wall
time, recovery steps (steps after an escalation or a blocked subgoal), completed subgoals per
System 2 intervention (delegation arms), missing-evidence failures (evidence arm). Guardrails: zero
false completions; every unauthorised destructive action paused; `evaluate` refusals counted as
pauses, not misses.

Routing in the delegation arms: System 2 decides when to delegate; S1 is not consulted on ordinary
System 2 steps. Confidence floors apply inside a delegation only. Authorization is a hard constraint
in every arm.

## Decision rule

- Supported on (a) to (c): delegation becomes the default loop; the reactive loop stays as a
  configuration. Evidence selection joins the default if its own predictions hold.
- Falsified on cost or completions: the reactive loop stays; delegation remains a tool System 2 may
  call. Record which subgoal classes failed (chosen wrongly versus executed wrongly), since that
  also answers Q4's planning-versus-execution question.
- `guarded` matches everything: the README's claim becomes "zero false completions and a gate at
  cost X", and S1's step speed is reported as a per-step number only.

## Result

Run `q9-live-dev-20260921-225012`, 55 tasks, four arms, one run each (`results/q9-live-dev.md`).
Verified passes 41 / 42 / 42 / 43 (guarded / dual / delegate / delegate+evidence); cost per verified
pass $0.0100 / 0.0117 / 0.0137 / 0.0140; zero false completions everywhere. Delegate costs 1.17× dual
per verified completion (prediction (b) falsified), reached 19 of 51 assignments (prediction (c)
falsified; the per-intervention denominator was mis-specified for a one-subgoal tool), and the
evidence arm did not cut System 2 tokens (falsified). The discriminating branch applies: guarded
matches every arm on completions within the intervals at the lowest cost. Dual keeps 26% fewer LLM
calls than guarded and the fewest steps; wall time is not distinguishable.

Caveats recorded: this run measured the first delegation build, which left assignments open across
System 2 steps (11 never closed, 2 reached with zero S1 steps) and asked the whole-task operation
question inside assignments; the coherent build (65da803) fixes both and is measured next. Four
saucedemo tasks failed for every arm including System 2 alone.

Decision under the rule: reactive loop stays the default; delegation and evidence remain tools;
README claim rewritten around the guard's cost.
