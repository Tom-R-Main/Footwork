# Q10. Does the arbiter's calibration transfer from DOM menus to accessibility-tree menus?

Pre-registered 2026-09-24, before any measured run on the native split. Build: commits 3fadd7e,
9163e79, c85647d and the P3 commit (native menu builder, NativeAgent, NativeS2, native runner).
Plan: `docs/plans/native-computer-use.md`. Survey: `docs/cua-notes.md`.

## Observation

The dual-process loop now runs on native macOS windows through Cua Driver with the browser
policy, prompts, arbiter thresholds (`arbiter.toml`), verifier and trace unchanged. Only the
menu builder is new: candidates come from the accessibility tree (role, label, value, enabled,
selected, section from labelled ancestors), page text is the window's static text plus text-field
values, and there is no `href`. Spikes (`results/native-spike-20260924/`) showed System 1 driving
Calculator and TextEdit at target confidence 0.52 to 1.00 with the same floors, and the verifier
accepting a typed sentence at complete 0.97. The oracle solvers pass 7/7 on the dev split
(`results/native-oracle-20260924/`).

On the web, Q1 found target confidence AUROC 0.80 on clicks and operation confidence 0.59
overall; the arbiter's floors are 0.55 (operation) and 0.45 (target).

## Hypothesis

H1: the calibration transfers. On native menus, System 1's target confidence predicts a right
click about as well as on the web (AUROC within 0.10 of 0.80 on labelled click rows), the
arbiter's floors give a false-escalation rate at or below the web's, and `dual` completes at
least as many dev tasks as `guarded` at lower cost per completion.

H0 alternatives: (a) confidence is flat or inverted on native menus because the signals that
carried it on the web (`href`, section names, page text) are absent; (b) System 1 completes the
clicks but the verifier cannot accept native end states (window text is too thin), so `dual`
loses to `guarded` on verified completions rather than on steps.

## Predictions

If H1 is true:
- `s1_only` passes at least 4 of the 7 dev tasks (the click-only Calculator tasks and the typing
  task); the two answer tasks fail by design (System 1 cannot compose an answer).
- `dual` passes at least as many as `guarded`, with fewer LLM calls per task.
- On the labelled S1 rows, target-confidence AUROC on clicks is at least 0.70 and the operating
  point at the current floors escalates no more than 20% of right steps.
- The verifier accepts the oracle end state of every non-answer task when asked directly.

If H1 is false:
- (a) AUROC on clicks below 0.65, or `s1_only` under 3 passes with escalations dominated by
  `target_confidence`.
- (b) `s1_only` steps reach the end state (predicate passes) but `is_done` stays false because
  every `done` is refused; `guarded` completes what `dual` does not, at higher cost.

## Design

- Split: `evals/native/tasks/dev.yaml` (7 tasks: 4 Calculator, 3 TextEdit; 2 answer tasks) with
  every oracle passing before the run. Tranche 2 (consent classes: Save over an existing file,
  Move to Trash, Delete; Finder, Dictionary, Preview, System Settings read-only, one Electron
  probe) is added by amendment before it is measured; nothing in tranche 1 is changed after.
- Arms: `s1_only`, `dual`, `guarded`. Three repeats per arm, same task order, one app at a time,
  fresh app instance per run.
- System 1: Jev 1.13 through `JevPolicy`, unchanged prompts (`PROMPTS_VERSION` in the header).
  System 2: Muse Spark 1.3 Contributor, `reasoning_effort=low`, 4000-token budget, the closed
  native action set. Verifier: the same `Verifier` and bands as the browser track.
- Labels: the Q1 protocol (two blinded Fable passes over blinded packets, agreed `model_label`,
  human audit of 40 rows) on every S1 decision row of the three arms, then `evals.calibration`.
- Runner: `uv run python -m evals.native.runner --split dev --arm s1_only --arm dual --arm guarded --repeats 3`.

## Primary metric and guardrails

Primary: verified completions per arm (predicate passed and `is_done`), paired by task across
arms with bootstrap 95% intervals on the difference (counts, not percentages, at n = 7).

Guardrails: crashes (launch failures, Driver refusals that end a run); false completions (a
claimed done whose predicate fails); paused runs on tranche 1 (there are no consent tasks, so any
pause is a false pause); estimated cost per verified completion.

Secondary: target-confidence AUROC on labelled click rows; false-escalation rate at the current
floors; per-step Driver effect words (share of `unverifiable`, `refused`).

## Decision rule

- H1 supported (all three: `dual` ≥ `guarded` on verified completions, AUROC ≥ 0.70, false
  escalation ≤ 20%): the native backend joins the default configuration with the browser
  thresholds; tranche 2 is pre-registered as an amendment and the consent gate is measured
  there before anything native is called safe.
- H0(a): the menu builder is the variable. Next experiment adds section and static-text context
  per candidate and re-measures; thresholds are not tuned on this split.
- H0(b): the verifier is the variable. Native end-state text gains structured fields (window
  title, focused control, dialog text) before re-measuring; System 2 is not made the default.
- Inconclusive (intervals cross zero and AUROC between 0.65 and 0.70): tranche 2 first, then
  re-decide on the pooled rows.

## Result (`results/q10-native-dev.md`, run `results/q10-native-dev-20260924`, 2026-09-24)

Verified completions of 21 per arm: `guarded` 11, `dual` 6, `s1_only` 6; predicate passes 17, 12,
11; no false completions, no pauses. Paired Δ(dual − guarded) −0.24 per task [−0.67, +0.10]. H1 is
not supported on the primary metric. On the secondary metric the calibration transfers: on 255
labelled System 1 rows (two blinded passes, kappa 0.74, human audit pending) target-confidence
AUROC for a wrong step is 0.90 [0.85, 0.94] (0.94 on acted rows) and the current floors escalate
5% of right steps, against 0.80 on the web. H0(a) is falsified. The completions `dual` lost went to
verifier refusals of correct end states (calc-subtract on every arm; the two answer tasks) and to
one task (calc-percent) where System 1 repeats a wrong key order after System 2 clears. Decision:
not adopted; verifier inputs and task wording are fixed and a repeated-sequence arbiter rule is
added before re-measurement; tranche 2 (consent classes) is pre-registered by amendment.

## Correction, 2026-09-24, from the secondary audit (`results/annotation/secondary-audit-20260924/`)

The audit re-read the traces and found three things the result above got wrong or left out:

1. **The append task's "verifier refusals" were execution failures.** Every System 1 and dual run
   typed "Second line." with `type`, which replaces the field's content, so the document lost its
   first line; the predicate only checked that the new line existed and passed the loss. The
   verifier's refusal of those dones was right. The count of 24 "wrong" rows on that task and the
   H0(b) attribution for it are withdrawn; the guarded runs did type both lines and were defeated
   by the newline collapse only.
2. **The authorization boundary did not cover keys, hotkeys, Return or menu paths**, and a failed
   destructive judgment fell through to allow. Fixed before anything else: `jevdual.authorize`
   is the one boundary every route passes (commit below), a failed judgment pauses, replacing a
   document's content pauses, and `append` exists as an operation that keeps content.
3. **The labels were not blind to the scores they evaluate**, the Calculator display was not in the
   packets, one repeat's six rows came from a trace outside the measured manifest, and the audit
   script collided repeats. The packet protocol is now protocol 2 (`RUBRIC.md`): no scores, window
   text and prior effects included, target/argument/completion split, manifest-joined rows, run
   identity in every key. The 0.90 AUROC stands as a ranking result on those labels; it is not a
   calibration claim, and the percent task alone gives 0.66.

## Amendment: Q10b, pre-registered 2026-09-24 before its run

Q10 stays as recorded. Q10b measures the corrected build on corrected tasks, in two stages.

**Stage 1, verifier acceptance on oracle end states.** For every dev task, replay its oracle, then
ask the verifier five times on the resulting window (same requirements, no trajectory) and record
the band and the `complete` and unmet probabilities. Prediction if the verifier is sound on native
end states: accept on at least four of five calls for every non-answer task whose requirement names
an observable (calc-multiply, calc-subtract, calc-percent, textedit-type-sentence,
textedit-append-line); the two answer tasks are asked with the oracle's answer and must accept
likewise. A task the verifier refuses on its own oracle end state is not run in stage 2 until its
requirement is rewritten (the rewrite is recorded here, and the pair before/after is kept).

**Stage 2, guarded vs dual on the corrected tasks.** Same arms, three repeats, `s1_only` as the
floor; tasks are the dev split with requirements naming observables (132, 175, 36), the
append-line task with the exact-file predicate, and Calculator reset to Basic mode before the run.
Primary metric unchanged: verified completions, paired by task. Guardrails add: **content
preserved** (no run may leave a document without its original lines; measured by the exact
predicate) and **boundary pauses** (every pause names its rule). Prediction if the dual arm's Q10
deficit was verifier and task artefacts: `dual` ≥ `guarded` on verified completions within one
task; if it was System 1's confident wrong sequences, the deficit stays on calc-percent alone and
a repeated-sequence rule for the arbiter is the next change (measured separately, not tuned here).

Costs and cadence: thresholds are frozen; nothing in `arbiter.toml` changes for Q10b except the
native keyword additions already made for the boundary; the heldout native split is created only
after Q10b and never debugged.

### Q10b stage 1 result (`results/q10b-verifier-probe-20260924*`, 2026-09-24)

Every oracle passed. Verifier acceptance of the oracle end state, five calls per task: without a
trajectory 3 of 7 tasks accepted at least four of five; with the oracle's steps as trajectory
(what a run carries) 5 of 7 accepted five of five. Rewrites recorded: calc-subtract, calc-percent
and calc-multiply requirements now name the displayed number (175, 36, 132; the arithmetic wording
was refused on calc-subtract 9 of 9 times in Q10); the append task's requirement went from "reads X
on the first line and Y on the second line" (unmet 0.35 to 0.46) to "contains both the line X and
the line Y" (accept 5 of 5, complete 0.83); the exact-file predicate carries the ordering and the
preservation check. The read task was reworded from "the second word" (counting, complete 0.48) to
"the word that follows brass" and still sits at complete 0.60 to 0.65 with unmet 0.15: a pure read
task has no action for the trajectory, and `complete` does not clear 0.80 on page evidence alone.
It is held out of stage 2 (`enabled: false`) as a verifier limitation to take to Q3, not tuned here.
Stage 2 runs on the six remaining tasks, Calculator in Basic mode.

### Q10b stage 2 result (`results/q10b-native-dev.md`, runs `q10b-native-dev-20260924` and `-r2`)

Verified completions of 18: `guarded` 15 / 15, `dual` 12 / 13, `s1_only` 9 / 9 (run 1 / run 2; run 2
adds labelled trajectory lines for the verifier, nothing else). No false completions; one boundary
pause; content preserved on every append run. Both amendment predictions held: the Q10 deficit was
mostly artefacts (calc-subtract and calc-read-result now verify on every arm), and the residual gap is
calc-percent, System 1's repeated wrong key order after a System 2 clear. append-line is verified by no
arm: the save has no readback, so the verifier is right to hold it. Protocol-2 labels on 246 rows:
kappa 0.93; operation-confidence AUROC 0.92 (all) / 0.94 (acted), target 0.87 / 0.88, with only 21
wrong rows in two tasks. Native stays experimental; next: save with readback, the repeated-sequence
rule measured alone, identifier hints for unlabelled controls, then tranche 2.
