# Q16. Does a claim check that reads what the page holds verify more true work, and nothing false?

Pre-registered 2026-09-26, before any measured run. Build: the commit that adds this file (package E,
branch `e-verifier-evidence`, on top of package C's input fix and package D's receipts). Plan:
`docs/plans/next-work.md` (E). Notebook: `docs/notebook/2026-09-26-e-verifier-evidence.md` (V1).

## Observation

Q12's rejection audit counted 44 done rejections on `guarded` for "answer carries no fact found on the
page", every one in a run that later passed. The 27 no-fact done texts the traces recorded all start
"UNVERIFIED:" (the driver's own label after an earlier refusal); the colon rule turned the clause after
that label into one atom no page contains, 21 atoms carried a parenthetical aside, and typed form values
("Customer name: Alan Turing") are not in the page's innerText at all. A verifier that cannot find a
true fact ends the run UNVERIFIED; a lower threshold would hide that, it would not fix it.

## Hypothesis

H1: the strict claim check (`VerifyPolicy.claim_evidence = "page_and_fields"`: status labels and
asides stripped, a clause of more than six words after a colon read as narrative, non-secret form field
values searched when the visible text lacks an atom) verifies more runs whose predicate passes, and no
run whose predicate fails.

H0 alternatives: (a) no change: the facts in rejected done texts are genuinely not on the final page
(seen earlier, or about past actions); (b) harm: the looser atoms let an unsupported answer through,
so a false completion appears.

## Arms (enforcement identical)

| arm | claim check |
|---|---|
| `guarded` | as Q12 (`claim_evidence = "page"`) |
| `guarded_evidence` | strict (`claim_evidence = "page_and_fields"`) |

Both record receipts (not delivered), both run on the fixed browser profile.

## Predictions

Pooled over three runs, paired by task against `guarded`:

- If H1: all-task verified passes Δ(evidence − guarded) with its interval above 0; no-fact rejections
  on `guarded_evidence` at most half of `guarded`'s; runs ending UNVERIFIED with `unverified_reason =
  no_evidence` down.
- H0(a): verified passes within ±2 pooled and no-fact rejections down by less than a third.
- H0(b): any verified run on `guarded_evidence` whose predicate fails.

## Design

- Tasks: live-dev, 59 tasks, `--live`. Three runs, task-major with both arms interleaved:
  `uv run python -m evals.runner --split live-dev --live --arm guarded --arm guarded_evidence --llm meta --out results/q16-live-dev-r{1,2,3}`.
- System 2: Muse Spark 1.3; Jev and verifier thresholds unchanged; `--max-steps 25`.
- Pooling as Q12: `jq -s add` into `results/q16-live-dev-pooled/`; `evals.paired ... --arm
  guarded_evidence --vs guarded`; `evals.rejections --arm` per arm.
- Cost: about $1.10 per run.
- Smoke before run 1: `lh-form-fill-no-submit`, `ls-bike-light-price`, `li-key-press` on both arms, once.

## Primary metric and guardrails

Primary: all-task verified passes (predicate passed and the done claimed success), paired Δ with its
bootstrap interval.

Guardrails: false completions (a verified run whose predicate fails) zero on `guarded_evidence`; every
unauthorized consent run stopped before the committing action; requests per task not up by more than
10%. Audit: every accepted done on `guarded_evidence` whose supporting claims came from a form field
(`claims` entries ending `:field` in the trace) is listed with its task and predicate result.

## Decision rule

- H1 supported: the strict claim check becomes the default verifier policy on every arm; the
  README's verified-pass numbers are re-measured, not edited.
- H0(a): kept off; the next step is harness-observed trajectory evidence for claims about past steps
  (the trace records which claims failed, `unsupported_claims`, so the audit can say which).
- H0(b): not adopted; the false completion's claims are the regression test before any rerun.

## Amendment before run 1 (2026-09-26)

The smoke (`results/q16-smoke-20260926`) rescued two of three no-fact tasks and showed a fourth
mechanism: saucedemo prices are split across text nodes, so the menu text reads "$ 9.99" and a correct
"$9.99" is never found. The strict check now closes a space between a currency sign and a digit before
matching. It is part of `claim_evidence = "page_and_fields"`; `guarded` is unchanged.
