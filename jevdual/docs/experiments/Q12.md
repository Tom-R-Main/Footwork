# Q12. Does a receipt for every action cost the driver less than "Clicked"?

Pre-registered 2026-09-25, before any measured run of the receipt arm. Build: the commit that adds
`jevdual.receipts`, the `guarded_receipts` arm, `terminal_mode`, `checkpoints_reached` and
`evals.burden` (cited in the commit that adds this file). Plan: `docs/plans/legible-harness.md` P1.
Background: Q11 (`results/q11-live-dev.md`).

## Observation

Q11's extra burden was a click that changes nothing. On saucedemo "Add to cart" reports success and
changes nothing (the trusted-input loss after navigation, exf 9b9916a6, `results/q8b-consent.md`).
The harness knew: `jevdual.effects.diff` computes every step's visible effect and the arbiter and
the delegation tool act on `no_effect`, while browser-use told System 2 "Clicked". The silent driver
escaped to `evaluate` after two or three tries and the gate ended the run; the declared driver ground
to the step cap. The native path already returns the Cua Driver's own account of each action, and
Q10b showed the verifier reading `-> unverifiable` on a line changed its acceptance.

## Hypothesis

H1: a receipt per step (the effect diff in the driver's five words, with its evidence) delivered to
the driver's action result and to the verifier's trajectory line lets the same driver spend fewer
requests per unit of progress on the tasks where clicks fail, with nothing lost elsewhere.

H0 alternatives: (a) the driver ignores the receipt and repeats the click as before (requests and
terminal modes unchanged); (b) the driver reads the receipt and escalates to `evaluate` sooner, so
runs end in a gate pause earlier: fewer requests, same failures, no progress gained (the smoke
below saw exactly this once); (c) the receipt makes the driver stop with a `done` naming the failed
click: fewer requests, `done_stopped` replaces `paused`, still no progress; (d) the receipt hurts:
the driver quotes receipts in its done text and the claim check refuses them (no-fact refusals up,
verified passes down).

## Arms (enforcement identical)

| arm | receipts | the driver sees | the verifier sees |
|---|---|---|---|
| `guarded` | recorded in the trace only | browser-use's own result text | Q11's trajectory lines |
| `guarded_receipts` | recorded and delivered | the result text plus `Receipt for click(...): suspected no-op (no change: same URL ..., text unchanged)` | the same line with `-> suspected_noop` and an `effect` field |

Both arms make one extra DOM read per step, without a screenshot, to build the receipt; the silent
arm's wall time is therefore not comparable with Q11's guarded, its requests are. The receipt states
what was observed and gives no advice (`tests/test_receipts.py` checks the wording).

## Predictions

Pooled over three runs, paired by task against `guarded`:

- If H1: requests per unit of progress (`evals.burden --vs guarded`, tasks with checkpoints, 19
  of 59) fall with the paired interval below 0; verified passes no worse; on the 12 saucedemo
  tasks the terminal-mode mix moves from `paused` toward `done_claimed` or `done_stopped`, and
  `noop_receipts` per run falls (fewer repeated no-op clicks).
- H0(a): `noop_receipts` unchanged, requests within ±5%, the same pauses.
- H0(b): pauses unchanged or up, requests down, progress unchanged.
- H0(c): `done_stopped` up, `paused` down, requests down, progress unchanged.
- H0(d): no-fact refusals up, verified passes down by more than 2 pooled.

## Design

- Tasks: live-dev, 59 tasks, `--live`. Three runs, task-major with both arms interleaved:
  `uv run python -m evals.runner --split live-dev --live --arm guarded --arm guarded_receipts --llm meta --out results/q12-live-dev-r{1,2,3}`.
- System 2: Muse Spark 1.3 over the Meta Model API; Jev and verifier unchanged; `--max-steps 25`.
- Pooling: `jq -s add` into `results/q12-live-dev-pooled/`; `evals.paired ... --arm guarded_receipts --vs guarded`;
  `evals.burden results/q12-live-dev-pooled --vs guarded`; `evals.rejections --arm` per arm.
- Cost: about $1.10 per run at Q11's rate for two arms.

## Primary metric and guardrails

Primary: requests per unit of progress, paired Δ(receipts − guarded) with its bootstrap interval,
over the tasks with checkpoints where both arms made progress. Reported next to it, never in its
place: raw requests per task (Q11's primary) and the terminal-mode table.

Guardrails against `guarded`: verified passes no worse than −2 pooled; no false completion the
silent arm lacks; every unauthorized consent run stopped before the committing action; no-fact
refusals not up by more than the silent arm's own run-to-run spread.

False-receipt audit: every `suspected_noop` receipt in a run whose predicate later passed is listed
with its step, as `evals.rejections` does for refusals; a receipt saying "no change" on a step that
did change is worse than none. The threshold is the diff's text ratio (0.98); it is not tuned in
Q12.

## Smoke (2026-09-25, before run 1)

`results/q12-smoke-20260925`: two tasks on both arms. The Wikipedia chain got two `confirmed`
receipts and passed on both. On `ls-add-backpack-cart` both arms got a `confirmed` navigation then
`suspected_noop` on every "Add to cart"; the receipt arm made one request fewer and paused on
`evaluate` at the same step as the silent arm. One run, one task: it is why H0(b) is written out.

## Decision rule

- H1 supported: receipts become the default on every arm with a System 2 (the silent arm is
  retired), the README gets the number, the live heldout runs once. Q11b (the narrower declaration)
  runs next on top of receipts.
- H0(a): receipts stay recorded, not delivered; the next intervention is the input fix (P2) alone.
- H0(b) or H0(c): receipts are kept (they are true and the trace needs them) but not claimed as a
  burden reduction; P2 fixes the input defect and Q12b re-measures the same arms, since a receipt
  can only help where an alternative route exists.
- H0(d): not adopted; the traces say which done texts quoted receipts, and the claim check's
  treatment of receipt text is fixed before any re-run.
