# Q13a. Does one contract hold across two surfaces when an operator drives?

Pre-registered 2026-09-28, before any measured task. Build: the commit that adds this file. Background:
`docs/plans/legible-harness.md` P5 (Q13); the oracle stage (notebook G8,
`results/q13-oracle-stage-20260928-010142`); the cross-surface pilot (G7). Q13 proper, with a model
driving a cross-app loop, follows once that loop exists (option 1); this is the operator form, as the
operator experience was measured on 2026-09-25.

## Question

When the operator (this Claude Code session, System 2) drives five cross-surface tasks through
`footwork` commands only, does every task end either done and proven by its oracle, or stopped with a
named reason, with no receipt that overstates, no effect beyond a grant, and a value's source kept from
the surface it was read on to the one it was used on?

## Tasks (start states made by script; the end state read by the oracles in `evals/crossapp.py` and `jevdual.carry`)

| # | task | surfaces | oracle |
|---|---|---|---|
| 1 | read the first book's price on books.toscrape.com, append it to a fresh TextEdit document, save | browser → TextEdit | `check-file --appended` |
| 2 | compute 48 × 13 in Calculator, send the result as the message of the fixture contact form (name Ada, email ada@example.com) | Calculator → browser | `one_submission(/confirm.html, message, 624)` |
| 3 | read the "Next search" line of a TextEdit note, search the fixture shop for it | TextEdit → browser | `one_submission(/search.html, q, quarterly report)` |
| 4 | download the fixture's quarterly report and open it in TextEdit | browser → Finder/TextEdit | `downloaded_and_opened` |
| 5 | read the order reference on the fixture's confirmation page, rename a scratch `draft.txt` to it | browser → Finder | `renamed` |

## Rules for the driver

- Effects only through `footwork` commands (`do`, `grant`, `read`, `snapshot-file`, `check-file`);
  no shell, osascript or manual step on the target apps during a task. Setup and the final oracle are
  scripted and outside the task.
- A gated effect (a send, a trash) is taken only with a `footwork grant` for exactly that effect.
- When the driver finds no route, the task ends with a written stop naming what was missing; that is a
  truthful stop, not a completion.

## Outcomes, per task

- Primary: completed and proven (the oracle confirms) / stopped truthfully (the last receipt or stop
  message names why) / failed untruthfully (the oracle fails while the receipts said the effect happened,
  or a stop message is wrong).
- Recorded: footwork commands issued, receipts by word, receipts contradicted by the oracle, pauses,
  grants issued and used, wall time from the first command to the last.

## Predictions

- Tasks 1, 2 and 3 complete and prove (routes exist: read, carry, type, click, grant, save).
- Task 4: the download completes; opening it in TextEdit through Finder (`do menu "File > Open"` on the
  selected file in a Finder window) is uncertain; either completed or a truthful stop.
- Task 5: the Finder rename is expected to stop truthfully (the plan recorded "rename unreachable: the
  rename field outside the target window"), unless a route is found.
- No task fails untruthfully; no receipt contradicted by an oracle; no effect without its grant.

## Decision

- All five either proven or truthfully stopped, none untruthful: the cross-surface contract holds for
  operator driving; the stops become the route work for option 1 (the cross-app loop), and Q13 proper
  (model-driven) is pre-registered on the same tasks and oracles.
- Any untruthful failure: the receipt or stop that misled is a defect fixed and tested first, before Q13
  proper.
