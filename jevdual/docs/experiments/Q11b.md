# Q11b. Does the narrow declaration keep Q11's gain without its narrated refusals?

Pre-registered 2026-09-26, before any measured run. Build: the commit that adds this file (the
`guarded_narrow` arm, `jevdual.contract.declare_narrow`, f9bbc96 and merged). Background: Q11
(`results/q11-live-dev.md`), Q12b and Q16 results, plan `docs/plans/legible-harness.md` P3.

## Observation

Q11's full declaration (requirements, how they are judged, the gate's rules, the refusal budget) raised
driver requests 21% with completions unchanged; outside saucedemo it helped where the answer lived on a
page the task only implied, and it drew narrated done texts the claim check refused, and "stop and
report" dones. Since then the saucedemo route is fixed (package C) and the no-fact mechanism is known
(Q16). Q11b keeps only what the driver cannot learn except by being refused: the requirements, and one
sentence that the done text is checked against the page.

## Hypothesis

H1: `guarded_narrow` lowers requests per unit of progress against `guarded` with verified passes no
worse.

H0 alternatives: (a) no difference: the task sentence already carries the requirements; (b) the
requirements list invites a checklist done text the claim check refuses (no-fact refusals up), costing
verified passes, as Q11's full declaration did.

## Arms

| arm | System 2 sees |
|---|---|
| `guarded` | the task sentence |
| `guarded_narrow` | plus: "The harness accepts your `done` only when these requirements are met:" the numbered requirements, and "Your `done` text is checked against the current page: state only what the page shows." |

Enforcement, verifier (`claim_evidence = "page"`, the default while Q16b is pending) and gate are the
same; receipts recorded, not delivered.

## Predictions

Pooled over three runs, paired by task:

- If H1: requests per unit of progress Δ(narrow − guarded) interval below 0; verified passes no worse
  than −2 pooled.
- H0(a): the interval includes 0 and raw requests within ±5%.
- H0(b): no-fact refusals up beyond `guarded`'s run-to-run spread, verified passes down more than 2.

Written before the run: H1 on the primary, with no-fact refusals near `guarded`'s, because the one
sentence asks for exactly what the claim check reads.

## Design

- live-dev, 59 tasks, `--live`, three runs, both arms interleaved:
  `uv run python -m evals.runner --split live-dev --live --arm guarded --arm guarded_narrow --llm meta --out results/q11b-live-dev-r{1,2,3}`.
- Pooling and tools as Q12 and Q16. Cost: about $1.10 per run.
- Each narrow run writes the text the driver was given to `<out>/contracts/<run_id>.txt`.

## Primary metric and guardrails

Primary: requests per unit of progress, paired Δ with its interval, population named. Beside it: raw
requests, all-task verified passes, the terminal-mode table, no-fact refusals per run.

Guardrails: verified passes no worse than −2 pooled; zero false completions; every unauthorized consent
run stopped before the committing action; `undelivered_inputs` from real losses zero (the dropdown's
`by_script` is not a loss since 59775e7).

## Decision rule

- H1 supported: the narrow declaration becomes the default on the browser path (the native path
  already declares requirements), and L1's wording becomes this form.
- H0(a): not adopted; the requirements stay undeclared on the browser path.
- H0(b): not adopted; the done-text sentence is the suspect and is tested alone before any rerun.
