## Recommendation

Make System One a replaceable **bounded decision role**. Keep Jev as one implementation and as
the current semantic risk/completion backend. Introduce Responses first through the existing System
Two callable, and compare its semantic judgments in shadow. Promote an alternative independently
for each role only after it wins that role's evaluation. Do not replace the execution/session runtime.

| Responsibility | Placement | Current decision |
| --- | --- | --- |
| Task reasoning, comparison, text composition, recovery proposals | System Two, behind Footwork commands | Responses is a suitable candidate transport; existing Muse remains the paired control. |
| Choose a bounded operation/target or abstain | Optional System One | Make the proposal contract portable; retain Jev's fast implementation. No evidence yet that Responses wins here. |
| Interpret the risk of a proposed action | Independent semantic risk judge | Keep Jev active during initial Responses driving; evaluate a replacement separately. Code owns permission. |
| Judge requirements against supplied evidence | Independent completion judge | Keep Jev active; shadow Responses on uncertainty cases, exposing raw judgments and deterministic refusals separately. |
| Pick source-linked evidence spans | Optional selector/ranker | Replaceable later; preserve exact spans, offsets, source identity and missing-evidence status. |
| Resource identity, freshness, authorization, effect multiplicity, dispatch and verified status | Deterministic Footwork code | Shared across providers; models cannot grant permission or invent an acknowledgment. |

The distinction is role versus model, not fast versus slow intelligence. A model may fill more than
one role, but each role needs its own contract, prompt, policy and measurements. Shared model identity
does not make an independent invocation an independent oracle. Use exact fixture/server/file oracles
for effects and labels authored before candidate execution for semantic questions.

## A portable contract that preserves meaningful differences

System One should receive a redacted observation, its revision, task/requirements, legal operation-target
pairs and bounded history. It returns a proposal or an explicit abstention/error. Record the selected
pair, optional ranked alternatives, source/evidence IDs, provider/model, prompt/schema versions and
usage. Code validates membership, revision, scope and effects before dispatch.

Keep numeric signals optional and identified by origin: native Choice distribution, native Noul score,
generated self-report, externally calibrated score, or unavailable. Preserve Jev's distributions
and speculative fan-out as capabilities of its adapter. An alternative need not synthesize every
conditional head or obey Jev's option/token cap if it has different limits. For a paired comparison,
both see the same evidence/candidate projection; provider-specific expanded context is a separate arm.

Never fill a chosen enum with probability 1.0, infer abstention probability from absent alternatives,
or feed an LLM's generated 0.8 into Jev's 0.8 threshold. Current code depends on distribution shape,
next-best margins, grouped conditional probabilities, independent absolute judgments and a ledger
whose carry/invalidation uses requirement kinds and unmet scores. Schema conformance proves none
of those semantics or their calibration. Jev's own calibration claims also remain limited by the
available human labels and measurements.

Separate proposal admission from judge admission. A candidate without validated uncertainty signals
starts in shadow; a bounded action pilot can use a deliberately narrow deterministic admissibility
rule and retain Jev risk/completion judgments. Uncertain, unsupported, failed or missing judgments
must remain explicit. Do not silently fall back to a less protective mode on errors. Preserve the
current Jev-only policy/configuration unchanged as a control rather than retuning its thresholds.

Risk judgments should classify the effect and bind it to supplied targets/context; they do not assert
that permission exists. Completion judgments should bind each requirement to supplied evidence,
return supported/contradicted/insufficient/unknown and distinguish historical effects from current
state. Code still decides acceptance and applies grounding, freshness and effect floors. Generated
explanations are audit aids; verified support comes from source-bound evidence, not rationale text.

## Current OpenAI guidance relevant here

Responses uses typed output items; custom tool results bind through `call_id`, and structured response
schemas use `text.format`. Start the offline role comparison without hosted tools; for a later command
integration, custom function calls can propose Footwork actions while local code controls dispatch.
The API transport is not itself a competitor model or a replacement for Jev's scorer.
[Official migration guidance](https://developers.openai.com/api/docs/guides/migrate-to-responses).

Use strict structured output for shadow judgments, with refusal/incomplete/error outcomes handled
explicitly. Structured Outputs constrains shape and can still contain semantic mistakes.
[Official Structured Outputs guidance](https://developers.openai.com/api/docs/guides/structured-outputs).

For independently paired shadow requests, use `store:false` and explicit supplied evidence. This
does not establish zero retention. Keep Footwork session state authoritative. If a later driver
preserves Responses reasoning context, replay the full applicable output items rather than only text;
do not convert opaque provider reasoning into portable domain memory.
[Official conversation-state guidance](https://developers.openai.com/api/docs/guides/conversation-state).

Initial candidate: `gpt-6-luna`, whose official model page supports Responses and structured output,
with reasoning effort configurable. Treat low effort as a pre-run setting for judgment trials,
not a guarantee of low latency or equivalence to Jev.
[Official model page](https://developers.openai.com/api/docs/models/gpt-6-luna).
Published Standard short-context prices are $0.10/M input and $0.50/M output; cache writes have
their own rate. Published pricing does not establish this account's access or actual trial cost.
[Official pricing](https://developers.openai.com/api/docs/pricing).
