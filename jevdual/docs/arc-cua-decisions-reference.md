# arc-cua reference: Decisions placement and the judgment boundary

Read-only source audit of `/Volumes/External SSD/referencerepos/arc-cua`, clean commit `6b353039111c08c2c64c5229083606941e364eaf`, version 0.1.1. Source hashes and scope: [receipt](../results/arc-cua-source-20261008/source.json). No reference checkout changes, installations, live execution or reproduced benchmarks.

arc-cua demonstrates that a finite-choice policy can support both Jev and Decisions. This makes a narrow transport seam practical; it does not establish that every System One role should be interchangeable. Our [D1](../results/d1-v2-dev-20261008/report.md) quality/speed result and [D2](../results/d2-dev-20261008/report.md) visual information result still determine placement: keep Jev active for text and validate Decisions for missing visual state.

The local OCR/AX split adds an alternative to paying for pixels on every call. Better text projection can let Jev handle some current visual-looking gaps; reserve image judgment for features text actually loses. Footwork already binds native menus to snapshot IDs and element tokens (`python/jevdual/native.py:115,609`), can capture screenshots on observation (`native.py:573`), and optionally live-rechecks target semantics (`native.py:622`). Its normalized NativeMenu does not currently carry screenshot bytes/hash/time for semantic judging. The practical new boundary is an observation-bound visual evidence envelope, not replacing the whole driver or loop.

## Boundaries to strengthen before transfer

arc's hybrid revision hashes element/guard and modal metadata, **not image pixels** (macos_hybrid.py:244). OCR freshness checks that the process and window still match, then returns true without recapturing/rechecking the visual target (macos_hybrid.py:388). Driver structure checks rely on journal changes and element-ID differences (driver.py:471). These are useful guards but cannot prove a color, chart or icon is unchanged. Visual adoption needs an explicit visual precondition and freshness policy alongside existing semantic binding; an image hash identifies a capture, it does not prove current state matches it. AX observation and capture are sequential rather than an atomic transaction.

The image completion merge keeps original text answers unless the image response explicitly refuses the same names (choice.py:237). A missing image verification answer can therefore inherit a text SATISFIED answer (choice.py:239); the OpenAI parser permits missing names (openai_decisions.py:147). This is a source-level transfer hazard, not a reproduced live failure. In Footwork, every requested visual check must supply a fresh, validated answer; missing, refused or malformed checks must not inherit prior positives.

The transport answers singleton questions with confidence 1 without a deterministic-source marker (openai_decisions.py:64), drops the full native response and permissively passes returned model/usage (openai_decisions.py:74), and dictionary parsing can overwrite duplicate question/option keys (openai_decisions.py:147). Retain our forced_single_option provenance and strict schema checks. Its request path retries failed calls (openai_decisions.py:82); our paid pilot deliberately makes no automatic retries and retains uncertain cost. The policy also retries invalid answers (choice.py:166); showcase usage totals omit discarded attempts and warm-up (examples/decisions_showcase.py:132). Retain durable per-attempt accounting. The shared policy's minimum confidence/margin is a heuristic, not calibration equivalence. Runtime completion verification is optional and defaults to true when absent (runtime.py:195); retain Footwork's existing completion and effect floors.

Screenshot transport is not covered by text secret redaction (README.md:249). Any future image study should use scoped, approved captures; this audit sent no real app captures. Model capacity to read an image is separate from an application's allowed evidence and execution authority.

## Speed evidence and next decision

arc's BENCHMARKS.md describes its own one-Mac driver comparison against cua-driver 0.32.0, with external postcondition checks. That is source-reported driver evidence, not our reproduced performance or a Decisions-versus-Jev model result. It also records missed delayed sheets, drag failures and thinner Electron observation, and notes development against the benchmark tasks (BENCHMARKS.md:68). The README's decision-loop table reports Jev runs; the provider-comparison example offers both providers but no retained authenticated OpenAI comparison results were established by this audit. Its example uses fixed provider order and successful-only elapsed medians (examples/compare_providers.py:127,144), so a Footwork comparison should retain randomized order and all attempts. Mocked transport tests establish contract handling, not API accuracy.

Driver, capture and settling costs could dominate full task latency even if model calls differ by a few milliseconds. Benchmark those separately before swapping the driver; do not multiply unrelated source/model speed ratios or hide delayed-reaction quality regressions inside a faster return time.

The next useful validation package is independent visual cases with blinded labels, adequate AX/OCR text as a control, exact capture/surface binding, a changed-after-capture refusal case, and capture-to-judgment plus independently checked effect latency. It should compare a dedicated image check to an every-step image policy and the improved Jev text projection. Only measured role-specific quality and speed should broaden interchangeability. No reference runtime or Footwork backend defaults were changed by this audit.
